Introduction

The Grails Passwordless Login plugin signs users in with a magic link or a passkey (WebAuthn), on plain Spring Security 7. It is not built on grails-spring-security-core, which assumes a password User/Role model.

The plugin owns the sign-in mechanics: single-use hashed login tokens, a confirmation page that keeps mail scanners from spending a link, rate limiting, passkey registration and sign-in, session establishment and a login form. The application supplies who the user is, how a link reaches them and what the session principal holds.

Usage

Installation

The plugin needs Grails 8, a GORM data source (it stores its login tokens with GORM and the passkeys with Spring’s JdbcTemplate on the same data source) and grails.serverURL.

dependencies {
    implementation 'io.github.gpc:grails-passwordless-login:1.0.0'

    // The plugin compiles against these but does not bring them in: the application decides the versions.
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.security:spring-security-webauthn'
}

Do not add grails-spring-security-core next to it; see Plain Spring Security, not the Grails Spring Security plugin.

grails.serverURL

Login links are built from grails.serverURL, never from the Host header of the request, which the requester controls. The links are also built on a background thread that has no request. The application refuses to start without it:

grails:
  serverURL: https://example.com

The same value gives the passkey relying party its id (the host) and its allowed origin; see Passkeys.

Schema

The plugin creates no tables on its own. An application that keeps its schema in Liquibase (grails-database-migration) includes the plugin’s changelog from its own:

databaseChangeLog = {
    include file: 'passwordless-login/changelog.groovy'
}

It creates three tables:

login_token

The plugin’s own. Holds the SHA-256 hash of each link’s token, never the token itself, when it expires and when it was used.

user_entities

Spring Security’s WebAuthn table for a passkey user, with a unique sign-in name (the email).

user_credentials

Spring Security’s WebAuthn table for the passkeys themselves.

The changelog is written for PostgreSQL. An application that does not use Liquibase must create the same tables itself, from that file.

Plain Spring Security, not the Grails Spring Security plugin

Most Grails applications use grails-spring-security-core. It is built around a password User / Role / UserRole model, @Secured annotations, springSecurityService and a grails.plugin.springsecurity.* configuration with its own filter chain. This plugin uses none of that. It is written against Spring Security 7 directly, and the application owns a normal Spring SecurityFilterChain.

What that means in practice:

  • Do not install both. Both would want to build the security filter chain.

  • There is no springSecurityService, no @Secured, no grails.plugin.springsecurity. and no UserRole domain.* Authorization rules go in the SecurityFilterChain, with authorizeHttpRequests.

  • There are no passwords. No chain accepts one. The plugin declares a UserDetailsService only because Spring’s WebAuthn support requires one after a passkey checks out; its password is a random value nobody knows.

  • The application decides what a user is. The plugin has no user domain class. It asks the application through three small interfaces (What the application supplies) and keeps the answer, the principal, in the HTTP session.

  • The current user is read the Spring way:

    import org.springframework.security.core.context.SecurityContextHolder

MyPrincipal principal = (MyPrincipal) SecurityContextHolder.context.authentication.principal

    The principal is whatever object the application’s LoginPrincipalFactory built.

  • Roles are authorities on the principal. hasRole('ADMIN') in the chain matches a ROLE_ADMIN authority returned by LoginPrincipal.getAuthorities().

  • Sessions, not tokens. A successful sign-in creates an ordinary HTTP session with Spring’s HttpSessionSecurityContextRepository. The session id is changed on sign-in against fixation, and CSRF protection is on, using HttpSessionCsrfTokenRepository.

If you are moving from grails-spring-security-core, the work is to write the chain (The security filter chain) and the three beans (What the application supplies), and to map your existing roles onto the authorities of your principal.

What the application supplies

The plugin owns the sign-in mechanics. The application supplies who the users are, how a link reaches them, and what the session holds. These are Spring beans, declared by name, either as Grails services (a service named sampleUserLookupService is a bean of that name) or in grails-app/conf/spring/resources.groovy.

Bean name Type and purpose Required

loginAccountLookup

LoginAccountLookup: finds a user by email and by id.

yes

loginLinkSender

LoginLinkSender: delivers a link by mail, SMS or whatever the application uses (see Sending the link).

yes

loginPrincipalFactory

LoginPrincipalFactory: builds the session principal, a LoginPrincipal.

yes

sessionPolicy

SessionPolicy: idle timeout per principal. Default is passwordless.session.idle for everyone.

no

loginSuccessRedirect

LoginSuccessRedirect: where a user goes after a magic link. Default is passwordless.login.successUrl.

no

A service whose class name matches the bean name needs no further wiring. Otherwise alias it:

// grails-app/conf/spring/resources.groovy
beans = {
    springConfig.addAlias('loginAccountLookup', 'userLookupService')
    springConfig.addAlias('loginPrincipalFactory', 'principalService')
    springConfig.addAlias('loginLinkSender', 'mailLinkSender')
}

LoginAccountLookup

Tells the plugin who can sign in. Return null for an unknown address, and for a user who must not sign in, such as a disabled one: the plugin treats both the same, and answers a request for a link identically either way.

@Transactional(readOnly = true)
class UserLookupService implements LoginAccountLookup {

    @Override
    LoginAccount findByEmail(String email) {   // already trimmed and lowercased
        account(User.findByEmailAndEnabled(email, true))
    }

    @Override
    LoginAccount findById(String id) {
        account(id?.isLong() ? User.findByIdAndEnabled(id.toLong(), true) : null)
    }

    private static LoginAccount account(User user) {
        user == null ? null : new LoginAccount(user.id.toString(), user.email, user.displayName)
    }
}

A LoginAccount holds only what the plugin needs: a stable id (a string, so any id type works), the lowercase email, which is the sign-in name and where links go, and a displayName that authenticators show next to a passkey. The lookup is called outside any transaction the plugin opens, so use your own, as above.

LoginLinkSender

Delivers the link. It receives the account, the complete URI, how long the link is valid and the optional context string the application attached when login started (see Context and the destination after sign-in).

class MyLinkSender implements LoginLinkSender {

    @Override
    void send(LoginAccount account, URI link, Duration validFor, String context) {
        // deliver `link` to `account.email`; see <<mail>> for a mail implementation
    }
}

By default (passwordless.async: true) the sender runs on a background thread, so the response to a request for a link takes the same time whether or not the address is known. It therefore has no request, session or locale to use. Exceptions are logged and do not reach the user.

LoginPrincipalFactory and LoginPrincipal

Called once someone has proved who they are, by link or passkey. It builds the object that lives in the session and that SecurityContextHolder returns. A LoginPrincipal needs an email, a passkeyVerified flag and its authorities, and may carry anything else: roles, memberships, a tenant.

final class MyPrincipal implements LoginPrincipal {
    final Long userId
    final String email
    final String displayName
    final boolean admin
    final boolean passkeyVerified
    // constructor ...

    @Override
    Collection<? extends GrantedAuthority> getAuthorities() {
        [new SimpleGrantedAuthority(admin ? 'ROLE_ADMIN' : 'ROLE_USER')]
    }
}

@Transactional(readOnly = true)
class PrincipalService implements LoginPrincipalFactory {

    @Override
    LoginPrincipal principalFor(LoginAccount account, boolean passkeyVerified) {
        User user = User.get(account.id.toLong())
        new MyPrincipal(user.id, user.email, user.displayName, user.admin, passkeyVerified)
    }
}

The principal is serialized into the HTTP session, so keep it serializable and free of domain objects, which would be detached and stale. Hold ids and values and look the rest up when needed. Because it is a snapshot, a role change takes effect at the next sign-in.

Sending the link

The plugin does not send mail. It has no mail dependency and no mail configuration. It builds the link and hands it to the application’s loginLinkSender bean (LoginLinkSender), which delivers it by whatever means the application has: SMTP, a transactional mail service’s API, SMS. This section shows one way to do it with Spring Boot’s mail support.

With Spring Boot’s JavaMailSender

Add the starter:

implementation 'org.springframework.boot:spring-boot-starter-mail'

Configure the SMTP server with Spring Boot’s own properties:

spring:
  mail:
    host: smtp.example.com
    port: 587
    username: login@example.com
    password: ${MAIL_PASSWORD}
    properties:
      mail.smtp.auth: true
      mail.smtp.starttls.enable: true

Then implement the sender:

import grails.plugins.passwordless.LoginAccount
import grails.plugins.passwordless.LoginLinkSender
import org.springframework.mail.SimpleMailMessage
import org.springframework.mail.javamail.JavaMailSender

import java.time.Duration

class MailLinkSender implements LoginLinkSender {

    JavaMailSender mailSender

    @Override
    void send(LoginAccount account, URI link, Duration validFor, String context) {
        SimpleMailMessage message = new SimpleMailMessage()
        message.from = 'Example <login@example.com>'
        message.to = account.email
        message.subject = 'Your login link'
        message.text = """\
            Hi ${account.displayName},

            Open this link to log in:
            ${link}

            It works once and expires in ${validFor.toMinutes()} minutes. If you did not ask for it, ignore this mail.
            """.stripIndent()
        mailSender.send(message)
    }
}

Declare it as loginLinkSender:

// grails-app/conf/spring/resources.groovy
beans = {
    loginLinkSender(MailLinkSender) {
        mailSender = ref('mailSender')
    }
}

An application that already uses the Grails Mail plugin, or an HTML mail template, does the same from send: whatever sends a message from ordinary code works here.

What the sender gets

  • account: the LoginAccount the lookup returned. account.email is the address to send to.

  • link: a complete, absolute URI, built from grails.serverURL (grails.serverURL). Put it in the mail as it is. Its last path segment is the token. Do not log it, and do not store it: whoever holds it can sign in until it is used or expires.

  • validFor: how long the link works, passwordless.login.tokenValidity.

  • context: the optional value the application attached when login started (Context and the destination after sign-in), or null.

How it runs

  • On a background thread. With passwordless.async: true, the default, the answer to the user is sent before the mail is. This is what keeps the response time the same for an address that has no account. The plugin’s executor has one to two threads and a queue of 200 requests.

  • With no request. There is no session, no request and no current locale. If the mail is in the user’s language, take the language from the user, not from the request, and format with a MessageSource and that Locale.

  • Inside a transaction. The token is saved and the sender is called in one transaction. If send throws, the token is rolled back and the failure is logged, and the user, who was already told "check your email", receives nothing and can ask again. Throw for a failure the user can fix by trying again. Do not retry for a long time inside send, which would hold a transaction and one of the two threads.

  • Without telling the user. An exception never reaches the person who asked. Watch the application log for Could not issue a login link.

  • In tests. In the test environment, or with passwordless.async: false, the executor runs the sender on the calling thread, so a test can ask for a link and read the result at once. A sender that keeps what it is given in a list, as the sample’s LinkInbox does, makes an integration test able to take the token from the link and redeem it.

Deliverability

The mail is a login credential, so it matters that it arrives:

  • Send from a domain with SPF, DKIM and DMARC set up.

  • Keep the mail short, in plain text, with the link on its own line. Some mail clients and scanners open links; this is why opening the link only shows a confirmation page and a button (Signing in with a magic link).

During development

Run a local SMTP catcher such as MailHog or Mailpit and point spring.mail.host at it in the development environment, or use a sender that writes the link to the log:

class LogLinkSender implements LoginLinkSender {

    private static final Logger log = LoggerFactory.getLogger(LogLinkSender)

    @Override
    void send(LoginAccount account, URI link, Duration validFor, String context) {
        log.info('Login link for {}: {}', account.email, link)
    }
}

Use it only in development: a link in a log is a login for anyone who can read the log.

The security filter chain

The application owns the SecurityFilterChain. The plugin contributes two calls that go into it, one before anyRequest() and one after:

@Configuration
@EnableWebSecurity
class SecurityConfiguration {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http, ApplicationContext context) {
        http.authorizeHttpRequests { auth ->
            auth.dispatcherTypeMatchers(DispatcherType.FORWARD, DispatcherType.ERROR, DispatcherType.INCLUDE).permitAll()
            PasswordlessSecurity.authorize(auth, context)       (1)
            auth.requestMatchers('/admin/**').hasRole('ADMIN')  (2)
            auth.anyRequest().authenticated()
        }
        PasswordlessSecurity.configure(http, context)           (3)
        http.build()
    }
}
1 Permits the pages anyone must reach before signing in, and guards the passkey registration endpoints.
2 The application’s own rules. Anything else it wants permitted without a login, such as /assets/**, goes here too.
3 Wires everything else the plugin needs.

Put this class in src/main/groovy of the application. Do not compile it with @CompileStatic: the Spring Security configurer DSL relies on closure-to-lambda coercion.

authorize permits /login, /login/, /webauthn/authenticate/ and /passwordless/ (the login pages, the passkey sign-in endpoints and the passkey script), and puts /webauthn/register/ behind the rule described in Passkeys.

configure sets, and the application should not override these on the same chain:

  • the HttpSession-based security context repository and CSRF token repository;

  • Spring’s WebAuthn support, with the plugin’s own sign-in success and failure handlers and without Spring’s default registration page;

  • an authentication entry point that sends an anonymous user to /login;

  • a NullRequestCache, so a user is not sent back to an old URL after signing in (see Context and the destination after sign-in for the plugin’s own way of choosing a destination);

  • logout: POST /logout, then /login?loggedOut. CSRF is on, so a logout button is a form with the CSRF token.

Everything else about the chain, such as headers, CORS and other matchers, is yours. An application with more than one chain, an API next to the web application say, applies the plugin only to the chain that serves browsers.

CSRF protection is Spring’s. A form rendered with <g:form> carries the token. A page that posts by script reads it from the page; <pw:csrfMeta/> in the <head> renders it as _csrf and _csrf_header meta tags.

Signing in with a magic link

The plugin serves these URLs:

GET /login

The login form. An email field and a button for a passkey.

POST /login

Asks for a link. Always redirects to /login/sent, whether or not the address is known.

GET /login/sent

"Check your email".

GET /login/token/{token}

A confirmation page. Opening a link only shows this page.

POST /login/token

Spends the token, signs the user in and redirects.

POST /logout

Spring Security’s logout.

Link a page to /login for an anonymous user, with <g:link controller="login" action="form">. An unauthenticated request for any protected page is sent there.

What happens

  1. The user posts an email address. The address is trimmed and lowercased and passed to loginAccountLookup.

  2. If it belongs to an account that is under its limit, the plugin creates a random token, stores its hash, and passes the link to loginLinkSender. If not, nothing happens and nothing differs in the answer. This is session recovery, not sign-up: it never creates an account.

  3. The user opens the link. The page asks them to press a button. This is deliberate: mail scanners and link previews fetch links with GET, and a GET does not spend the token.

  4. The button posts the token. It is accepted once, and only before it expires (passwordless.login.tokenValidity, 15 minutes). Two simultaneous attempts cannot both succeed.

  5. The plugin asks loginPrincipalFactory for the principal, changes the session id, issues a new CSRF token, sets the session’s idle timeout from sessionPolicy, and stores the principal in the session.

  6. The user is redirected to the URL loginSuccessRedirect returns.

An invalid, used or expired token sends the user back to /login with a notice.

Rate limits

Two sliding windows, both per passwordless.login.rateLimit.window:

  • Per account, perAccount links (default 5). Silent: the user gets the normal answer and no mail, since a visible answer would reveal that the address is known.

  • Per address, perAddress requests (default 20) from one remote address. Answered with 429 and a "too many requests" page. This says nothing about whether any address is known.

The limits are kept in memory, per application instance. Behind a reverse proxy, make sure request.remoteAddr is the client’s address, for instance with Spring Boot’s server.forward-headers-strategy, or every user counts against the proxy’s address.

Context and the destination after sign-in

A request for a link can carry a free-text context of up to 100 characters, for example the tenant the user was signing in to. Put it in a hidden field on the login form, or a request parameter on /login?context=acme: the plugin’s form passes it on. It is stored with the token, handed to LoginLinkSender.send(…​) so the link can say where it is for, and handed to LoginSuccessRedirect.urlFor(principal, context) when the link is spent.

class TenantRedirect implements LoginSuccessRedirect {

    @Override
    String urlFor(LoginPrincipal principal, String context) {
        context ? "/t/${URLEncoder.encode(context, 'UTF-8')}/" : '/'
    }
}

// resources.groovy
beans = {
    loginSuccessRedirect(TenantRedirect)
}

The result must be a path on the application, starting with a single /. Anything else, a full URL or //host, is replaced with /, so a crafted link cannot send a user to another site.

Binding a session to something

SignInService.bind(principal, request, response) replaces the principal of the current session without a new session id. An application that rebinds a session, to another tenant say, builds a new principal and calls it.

Session length

The session’s idle timeout is passwordless.session.idle (ISO-8601, default 14 days). To vary it by user, declare a sessionPolicy bean:

class MySessionPolicy implements SessionPolicy {

    @Override
    Duration idleTimeout(LoginPrincipal principal) {
        ((MyPrincipal) principal).admin ? Duration.ofMinutes(30) : Duration.ofDays(14)
    }
}

// resources.groovy
beans = {
    sessionPolicy(MySessionPolicy)
}

Expired tokens are kept for a day and deleted when the next link is issued.

Passkeys

A user who has a passkey can sign in with it from the login form, without waiting for an email. Registering and signing in happen in the browser against Spring Security’s WebAuthn endpoints (/webauthn/*, /login/webauthn). The plugin adds the pages and the rules around them.

GET /account/passkeys

The signed-in user’s passkeys: list, add, remove.

POST /account/passkeys/delete

Removes one of the user’s own passkeys.

GET /account/passkeys/confirm

Asks the user to confirm a passkey, or add the first one.

GET /passwordless/passkeys.js

The script behind the buttons. Served from the plugin’s jar, so there is no asset to set up.

Link to /account/passkeys from the application, for example from a user menu.

The relying party

WebAuthn ties a passkey to a host name. By default the plugin uses the host and origin of grails.serverURL (grails.serverURL), and passwordless.app-name (or passwordless.passkeys.rp-name) as the name shown in the browser’s dialog. Browsers must reach the application at that name: a passkey made at https://example.com does not work at another host, and changing the host later orphans every passkey. Browsers allow passkeys on localhost over plain HTTP, and nowhere else.

Who may add or remove a passkey

A session from a hijacked mailbox must not be able to add its own passkey to an account that already has one. So:

  • A user without a passkey may add their first.

  • A user with one may add or remove passkeys only in a session that has confirmed one, that is, whose principal has passkeyVerified == true. A passkey sign-in sets it. A magic link sign-in does not.

A user who signed in with a link and wants to add or remove a passkey is sent to /account/passkeys/confirm, which asks for an existing passkey. Afterwards they go to the page they were heading for (see below), or to passwordless.login.successUrl. A session that has already confirmed a passkey and opens the page is sent on to passwordless.passkeys.confirmedUrl.

The rule is enforced on the registration endpoints in the chain, not only in the pages.

Asking for a confirmed passkey

An application can demand a passkey for a sensitive page: check passkeyVerified and send the user to confirm one, remembering where they were going.

def admin() {
    MyPrincipal principal = (MyPrincipal) SecurityContextHolder.context.authentication.principal
    if (!principal.passkeyVerified) {
        session.setAttribute(PasskeySignInHandler.RETURN_TO, '/admin')
        redirect controller: 'passkey', action: 'confirm', method: 'GET', absolute: false
        return
    }
    // ...
}

After the passkey is confirmed the user is sent to the saved path, which must be a path on the application, otherwise to passwordless.login.successUrl. A confirmation signs in again, through loginPrincipalFactory with passkeyVerified = true.

Telling the user

When a passkey is added, the plugin publishes a Spring PasskeyRegisteredEvent carrying the user id and the label. Listen to it to send a "a passkey was added to your account" mail, to the user and to whoever else should know:

class PasskeyNotifier {

    @EventListener
    void onRegistered(PasskeyRegisteredEvent event) {
        // look up the user from event.userId, send a mail
    }
}

// resources.groovy
beans = {
    passkeyNotifier(PasskeyNotifier)
}

Requirements

Passkeys need a secure context: HTTPS, or localhost. The login form still works for links when passkeys cannot. The plugin declares exactly one UserCredentialRepository bean, userCredentialRepository. Do not declare another: with two, Spring Security’s WebAuthn configuration ignores both.

Customizing the pages

The plugin ships the login pages (login/form, login/sent, login/confirm, login/tooMany) and the passkey pages (passkey/manage, passkey/confirm) as GSPs that use layout="main". Two ways to change them:

  • Layout. The pages are decorated by the application’s main layout, so they take on its look. The sample layout and the plugin’s markup use Bootstrap classes.

  • Replace a page. A view with the same path in the application, say grails-app/views/login/form.gsp, wins over the plugin’s. Keep the form fields (email, an optional context) and the same targets. A page with passkey buttons needs <pw:passkeyScript/> in its head and <pw:csrfAttrs/> on the element carrying data-passkey-scope; copy the plugin’s page as a starting point.

  • Text. All text is in message bundles, passwordless-login.properties and a Danish passwordless-login_da.properties. Override a key in the application’s grails-app/i18n/messages.properties, or add another language the same way.

The pw tag library offers <pw:appName/>, <pw:csrfMeta/>, <pw:csrfAttrs/> and <pw:passkeyScript/>.

A complete example

examples/sample in the repository is a small application that uses the plugin the way an application would: a GORM SampleUser, a lookup service, a principal and its factory, a session policy, an in-memory link sender, and the security chain, with integration specs that run on PostgreSQL with Testcontainers. It is the best reference for how the pieces fit.
